状态码：服务器在跟你说什么

2026-09-14 · API 系列 · 第一篇

调用接口时，服务器返回的那个三位数字，是它在用最短的方式告诉你"刚才这件事怎么样了"。读懂它，排错效率会高一大截；读错了，就会在完全错误的方向上折腾半天。

一、数字开头的含义：按责任划分

这不是随便定的编号，而是按"问题出在谁身上"分类的：

  • 1xx —— 信息类。服务器说"收到了，还在处理，你先等着"。平时基本见不到，除了 WebSocket 升级时的 101。
  • 2xx —— 成功。最常见的 200，还有创建成功的 201、接受了但异步处理的 202、没有正文的 204。
  • 3xx —— 重定向。东西不在这，去别处找。301 永久、302 临时、304 缓存还有效。
  • 4xx —— 客户端的错。你请求错了：地址不对、没权限、参数有问题、请求太频繁。
  • 5xx —— 服务端的错。服务器那边崩了、超时了、配置错了。
这个划分的实用价值极高：看到 4xx，去改自己的代码和参数；看到 5xx，那就是对方的问题（或者你把它搞崩了，但至少不是请求格式问题）。方向完全不同。

二、几个必须记住的

200 OK

成功。但要小心一个坑：有些接口设计得不好，出错也返回 200，把错误信息塞在正文里，比如 {"code": 500, "msg": "失败"}。这种情况下看 HTTP 状态码没用，必须看返回体的业务码。见到过这种设计，就知道不能只判 status。

301 和 302

  • 301 永久重定向。浏览器和搜索引擎会记住，以后直接去新地址。适合换域名、合并 www 与裸域。
  • 302 临时重定向。不缓存，每次都问原地址。适合登录后跳转、灰度切换。

这两个搞反的后果很实际：该用 302 用了 301，浏览器永久记住了错误的跳转，改都改不回来，用户得清缓存。

304 Not Modified

浏览器带着 If-None-Match 问你"这个东西还是那个版本吗"，你回 304，表示"没变，用你缓存的"，响应不带正文。这是最省流量的一个状态码，静态资源应该充分利用。

400 Bad Request

请求本身格式有问题——JSON 语法错了、必传参数没传、字段类型不对。看状态码不够，一定要看返回体的错误详情，通常会指明是哪个字段。

401 和 403 —— 最容易搞混的一对

  • 401 Unauthorized：你没告诉我你是谁。没带 token、token 过期了、token 格式不对。解决办法是去认证再重试。
  • 403 Forbidden：我知道你是谁，但你不能干这个。带了有效 token，但权限不够；或者 IP 被限制；或者这个资源不允许这个方式访问。

记住区别的方法：401 是"先登录"，403 是"登录了也没用"。

404 Not Found

资源不存在。常见原因：路径拼错、大小写不对（服务器是 Linux 时区分大小写）、资源被删了、路由没配。

这里有个重要细节：接口设计里，404 不该被滥用。比如查一个不存在的用户，返回 404 还是 200 加空数据，是个设计选择，没有绝对对错，但一个接口里要一致。

429 Too Many Requests

请求太频繁，被限流了。通常响应头会带 Retry-After 告诉你要等多少秒。写爬虫或者批量调接口时最常撞上这个。

正确的处理方式是指数退避：第一次等 1 秒，第二次 2 秒，第三次 4 秒，别硬刚。

500 和 502 / 503 / 504

  • 500 Internal Server Error：后端代码抛异常了。最笼统的一个错误。
  • 502 Bad Gateway：反向代理（Nginx 之类）连不上后面的应用服务。常见于应用崩了没重启。
  • 503 Service Unavailable：服务暂时不可用，可能是过载或者维护中。
  • 504 Gateway Timeout：代理等后端响应等到超时了。后端处理太慢或者卡住了。

502 和 504 的区别值得记一下：502 是"连不上"，504 是"连上了但等不到回复"。

三、一张速查思路

遇到非 2xx 时，按这个顺序想：

  1. 看是不是 3xx。是的话多半是正常跳转，检查最终落到哪个地址。
  2. 是 4xx 吗？那问题在我这边。逐个排除：地址对不对 → 参数全不全 → 认证信息有没有 → 权限够不够 → 是不是请求太频繁。
  3. 是 5xx 吗？那问题在服务端。先重试一次（可能是瞬时故障），持续出现就要去看服务端日志，或者联系接口提供方。
  4. 永远是"看返回体"。状态码只是分类，具体原因在返回体的错误信息或错误码里。

四、动手看一眼真实的响应

不用装任何东西，命令行就能看：

curl -i https://example.com              # 打印响应头 + 正文
curl -I https://example.com              # 只打印响应头（HEAD 请求）
curl -o /dev/null -s -w "%{http_code}\n" https://example.com   # 只要状态码
curl -L https://example.com              # 自动跟随重定向，用来看 301/302 的最终落点

浏览器里更直观：开发者工具 → Network 面板 → 点任意一个请求，Status 那一栏就是状态码，Response Headers 里能看到全部响应头。

一个实用技巧：排查跳转问题（比如登录后跳错页面、www 和裸域来回跳）时，用 curl -IL，它会把每一跳的响应头都打出来，能清楚看到中间经过了几个 301/302。

五、设计接口时怎么用好状态码

如果你以后要写接口，有几点值得坚持：

  • 用对状态码，别全返回 200。虽然前端处理麻烦一点，但客户端、监控、日志全都能受益，出问题时一眼看出是哪类错误。
  • 错误响应体要统一结构。比如固定 {"error": "...", "detail": "...", "request_id": "..."}，客户端才能统一处理。
  • 带上 request_id。用户报错时给你这个 ID，你能直接在后端日志里捞出那一条。这是运维上非常省事的一个设计。
  • 别泄露内部信息。500 的返回体里不要出现堆栈、SQL 语句、文件路径。详细的记在服务端日志里就好。

六、几个容易踩的认知坑

  • "200 就一定成功。" 上文说过，业务错误可能也返回 200。
  • "403 就是没登录。" 不是，是登录了没权限。没登录是 401。
  • "500 是服务器坏了。" 不一定，很多时候是某个参数触发了后端的 bug。同一个接口，换一组参数就正常。
  • "429 换个 IP 就行。" 能绕，但如果是自己的接口调用，正确做法是加退避和限流，而不是对抗。
  • "状态码是 HTTP 规范严格规定的。" 只有分类（1-5 开头）是强约束，具体用哪个数字很大程度是行业惯例，不同接口可能不一致。
小结。状态码是服务器发给你的一份极简诊断报告——第一位告诉你责任方（4 是客户端、5 是服务端），后两位告诉你具体情况。养成"看到状态码 → 判断责任方 → 再去看返回体详情"的习惯，接口调试会快很多。
