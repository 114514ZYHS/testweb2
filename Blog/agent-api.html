给 AI Agent 写一个 API：它和人类用起来有什么不一样

2026-09-14 · Agent 系列 · 第一篇

Agent 正在成为接口的重要调用方。它不像人那样能"猜"、能"看懂一个大致的说明"、能在报错时自己摸索着改。这些差异，反过来会改变接口该怎么设计。

一、Agent 是最挑剔的调用方

一个典型的 Agent 工作方式是：给它一个目标，它自己决定调哪些工具、按什么顺序调、失败了怎么办。它没有眼睛去看你的界面，没有常识去补全你的暗示，也不能打开浏览器去搜一下"这个报错是什么意思"。

所以对人类来说"差不多能用"的接口，对 Agent 来说可能是完全不可用的。它需要的性质其实是：

  • 自描述。接口有什么能力、参数是什么类型、有哪些取值范围，必须明确写出来。
  • 错误可理解。失败时给出的是"哪个参数错了、应该是什么样"，而不是一个错误码。
  • 结果可判断。调用完，Agent 要能确凿地知道做成了没有。
  • 幂等或可查询。它一定会重试，因为网络会抖、它会判断失误。重试必须安全。

二、工具的粒度：太大和太小都不行

把能力暴露给 Agent 时，第一个要做的选择是粒度。

粒度太粗

do_thing(action: string, params: object)

这等于把一个万能入口丢给 Agent——它得猜 action 该填什么、params 里有什么，而且模型看不到每个动作的具体参数定义，只能瞎猜。结果就是反复试错、大量无效调用。

粒度太细

open_file()
read_line()
read_next_line()
close_file()

这会让一个简单任务变成十几个来回，每一步都在消耗上下文和 token，还容易在中途"忘了自己在干什么"。

合适的粒度

大致是"一个语义完整的动作"——人类操作员会一次做完的事。比如 search_articles(query, limit)、create_invoice(customer_id, items)、run_tests(path)。每个函数名字本身就是一句说明。

一个判断方法：如果你的工具描述需要写超过一句话才能让 Agent 明白用途，那它可能太大了，该拆；如果两个工具永远连在一起调用，那它们可能太小了，该合。

三、描述文本是接口的一部分

对 Agent 来说，函数的描述文本和参数说明就是它的全部信息来源。这不是文档，这是接口本身。

对比一下：

名字：process(data)
描述：处理数据。

名字：resize_image(path, width, height)
描述：把本地图片缩放到指定像素尺寸，并覆盖写回原文件。
      width 和 height 都是像素，必须是 1 到 4096 之间的整数。
      如果图片本身比目标尺寸小，不会放大，直接返回原路径。
      失败时返回错误信息，原文件不变。

第二个描述里包含了 Agent 做决策需要的一切：干什么、单位是什么、取值范围、边界行为、失败时的状态。这些不是"冗余说明"，而是"接口契约"。

值得写进去的几类信息

  • 副作用。会不会改文件、发请求、花钱、发消息。这一条极其重要，Agent 需要知道哪些操作不可逆。
  • 幂等性。调用两次会不会产生两个结果。
  • 边界行为。空输入怎么办、超限怎么办、找不到怎么办。
  • 单位。秒还是毫秒、字节还是 KB。这类参数一旦搞错，后果很具体。
  • 返回值结构。成功返回什么、失败返回什么。

四、错误信息：写给 Agent 看，也写给"修复"看

Agent 拿到错误后要做的不是"显示给用户"，而是决定下一步怎么办。所以错误信息要能支撑这个决策。

差的：{"error": "invalid input"}

好的：
{
  "error": "invalid_parameter",
  "message": "参数 retry 必须是 0 到 5 之间的整数，收到的是 -1",
  "field": "retry",
  "retryable": false
}

多出来的两个信息特别关键：

  • 哪个字段错了。Agent 可以精确修正这一个参数重试，而不是推翻整个调用。
  • retryable。告诉 Agent"这个错误重试有用吗"。参数错误重试一百次都是错的；而临时故障重试就可能成功。没有这个信号，Agent 只能盲目重试或者盲目放弃。

五、幂等与"重试安全"

Agent 一定会重试。可能因为网络超时，可能因为它自己判断错了。所以每个会产生副作用的操作都要问一句：重试一次会怎样？

  • 读取类操作天然安全。
  • 更新类操作如果是"设为某个值"，多次执行结果一样，安全。
  • "增加"类操作（扣款、加库存、发通知）必须引入幂等键。调用方带一个唯一 ID，服务端看到重复 ID 就返回上次的结果，不重复执行。
POST /payments
Idempotency-Key: 7f3a-91c2-4d8e

这个机制在主流的支付接口里已经是标配。当调用方是 Agent 时，它不是"锦上添花"，而是必需品。

六、别让 Agent 面对无限可能

人类可以接受"这里填一个任意字符串"，Agent 面对开放参数时容易生成看起来合理但完全没用的内容。

能收窄就收窄：

  • 枚举代替自由文本。状态参数给 pending / active / closed 三个选项，别让它自由发挥。
  • 格式写明。日期写清 YYYY-MM-DD，不要只说"日期"。
  • 给示例。描述里带一个真实可用的例子，Agent 会照着仿写，正确率明显提高。
  • 参数数量控制住。一个函数十几个参数，模型填错的概率显著上升。考虑分组，或者拆成几个函数。

七、返回结果：省 token 也是设计目标

Agent 的上下文窗口是有限的，而每一次工具调用的返回结果都要塞进去。所以：

  • 别返回一大堆用不上的字段。一个用户对象返回 40 个字段，Agent 只需要其中的名字和 ID，那 38 个字段就是纯浪费。
  • 提供精简视图。比如 ?fields=id,name,status 让调用方自己选。
  • 长列表要分页。并且默认页大小别太大。
  • 大内容给引用而不是正文。比如返回一个大文件的下载地址，而不是把几兆内容塞进上下文。
  • 结构化优先。同样信息用 JSON 比一大段自然语言更好解析、更省 token。
一个容易忽略的点：错误日志、堆栈、HTML 页面这些"对人类友好"的返回，对 Agent 是灾难——它会尝试把一堆无意义的标签和路径读进上下文，既浪费又容易误导。面向 Agent 的接口应该只返回结构化数据。

八、给危险操作加护栏

Agent 会犯错，而且犯错的方式和人类不同：它可能更"遵守规则"地执行一个错误的指令。所以：

  • 破坏性操作要显式确认。删除、覆盖、批量修改、发送对外消息——这些应该要求一个明确的确认参数，而不是默认执行。
  • 权限最小化。给 Agent 的凭证只开放它真正需要的范围。不要给它一把能开所有门的钥匙。
  • 可回滚。软删除优于硬删除。改之前留副本。这样出错还能救。
  • 可审计。每次调用都记下来：谁调的、什么参数、什么结果。出问题时要能还原现场，这是事后复盘的唯一依据。
  • 限制影响范围。一次最多删多少条、最多花多少钱、最多发多少条消息，设个硬上限。

九、让 Agent 知道自己"能做什么"

工具列表本身就是 Agent 的能力清单。它按照这份清单来判断"这个任务我能不能做"。

所以：

  • 工具数量别失控。几十个工具会让选择变得困难，还会占满上下文。可以考虑分组或者按场景动态加载。
  • 名字要有区分度。get_user 和 fetch_user 这种名字会让 Agent 随机挑一个，该合并或者明确区分用途。
  • 明确冲突时的取舍。如果有两个工具功能重叠，描述里要说清什么时候用哪个。

十、和人类接口的差别，一句话概括

人类接口的隐含假设是"使用者会自己补全上下文、会搜索、会求助"。Agent 接口的假设是：使用者只会读你写下的东西，然后严格照做。

所以设计重点从"界面友好"变成了"契约完备"：

  • 人类接口：描述可以省略，用户会摸索。
  • Agent 接口：描述必须完整，因为没人会摸索。
  • 人类接口：报错可以笼统，人能猜。
  • Agent 接口：报错必须指明字段和可否重试。
  • 人类接口：误操作可以点确认挽回。
  • Agent 接口：必须先设计好幂等和上限。
小结。给 Agent 写接口，本质上不是"新的技术"，而是把接口契约写严谨这件事重新变得重要——因为这一次，调用方真的会一字一句照着你写的东西执行，一个字没写清楚，就是一次失败的调用。把每个工具当成"要交给一个很听话但完全没有常识的新同事"，设计方向就对了。
