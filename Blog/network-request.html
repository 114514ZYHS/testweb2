从敲下网址到看见页面：一次网络请求的完整旅程

2026-09-14 · 网络系列 · 第二篇

上一篇讲了域名和 DNS。这一篇把整个过程串起来：从你敲下回车，到浏览器把页面画出来，中间到底经过了多少层。理解了这条链路，网速慢、网页打不开、图片加载失败这类问题，你就能自己定位到大概哪一段出了毛病。

一、总览：七个阶段

一次典型的首次访问，按顺序是：

  1. 解析域名。把 example.com 变成 IP。
  2. 建立 TCP 连接。和服务器握手，建立可靠通道。
  3. 建立 TLS 加密。握手协商密钥，把通道加密。
  4. 发送 HTTP 请求。告诉服务器你要什么。
  5. 接收响应。服务器返回状态码、响应头和正文。
  6. 解析渲染。浏览器把 HTML/CSS/JS 变成画面。
  7. 加载子资源。图片、字体、脚本，重复前几步。

下面逐段说。

二、传输层：TCP 的三次握手

HTTP 是"应用层"的协议，它自己不负责把字节可靠地送到对面。这个活是 TCP 干的。TCP 建立连接要三次握手：

客户端 -> 服务器：SYN，我想连你
服务器 -> 客户端：SYN + ACK，收到，我也想连你
客户端 -> 服务器：ACK，好，连上了

为什么是三次不是两次？因为要双方都确认对方的收发能力正常。两次的话，服务器无法确认客户端能收到自己的包。

代价是：建立连接本身要花一个来回（RTT）。跨洋访问一个 RTT 可能 200 毫秒，还没传数据就先花掉 200 毫秒，这就是为什么 CDN 有用——把服务器搬到离你近的地方。

后来有了 TCP 快速打开（TFO）和 QUIC（基于 UDP 的一套新传输协议，HTTP/3 用它），把握手次数压下来。QUIC 甚至能做到 0-RTT 恢复。

三、TLS 握手：不只是"加密一下"

HTTPS 就是 HTTP over TLS。TLS 握手要做三件事：验证对方身份、协商加密算法、交换密钥。

简化后的流程（TLS 1.3）：

  1. 客户端说：我支持这些加密套件，这是我的一次性公钥。
  2. 服务器回：我用这个套件，这是我的证书，这也是我的一次性公钥，附带用私钥做的签名。
  3. 双方各自用对方公钥 + 自己的私钥，算出同一个会话密钥。

之后所有数据用对称加密（通常 AES 或 ChaCha20）传，因为对称加密速度远快于非对称。

一个常见误解："HTTPS 是不是让网站变快了？" 不，HTTPS 是变慢一点的——多了握手、多了加解密开销。现代优化（TLS 1.3 的一次往返、会话复用、硬件加速）把这个开销压得很小，但不等于没有。HTTPS 换来的东西是机密性和完整性，不是速度。

四、HTTP 请求长什么样

一个 GET 请求，去掉各种头之后本质是：

GET /Blog/index.html HTTP/2
Host: www.4444442.xyz
User-Agent: Mozilla/5.0 ...
Accept: text/html,application/xhtml+xml
Accept-Encoding: gzip, deflate, br
Cookie: ...

关键点：

  • 方法（GET/POST/PUT/DELETE）表示想干什么。
  • 路径是要的资源。
  • Host 指定域名——同一台 IP 上可能有很多网站，靠这个区分。
  • Accept-Encoding 表示我能解压，服务器可以压缩后发。这能省一半以上流量。
  • Cookie 是服务器之前发给你的凭证，自动带上。这也是为什么追踪能跨页面。

关于 HTTP 方法和状态码的细节，见状态码那篇。

五、响应：状态码 + 头 + 正文

HTTP/2 200 OK
content-type: text/html; charset=utf-8
content-length: 4826
cache-control: max-age=600
etag: "5f3a-2f1b"

<!DOCTYPE html>...
  • 200 成功。301/302 跳转。404 找不到。500 服务器出错。
  • content-type 决定浏览器怎么解释这些字节。写成 text/plain 的 HTML 不会被渲染，会直接显示源码。
  • cache-control / etag 决定能不能用本地缓存。用得好，第二次访问几乎不发请求。

条件请求：省流量的关键

浏览器第二次请求同一个资源时，会带上 If-None-Match: "5f3a-2f1b"。服务器对比后如果没变，直接回 304 Not Modified，不带正文。省下的就是整个文件的流量。

六、渲染：真正慢的地方往往在这

拿到 HTML 之后，浏览器要：

  1. 解析 HTML，构建 DOM 树。
  2. 解析 CSS，构建 CSSOM。CSS 是阻塞渲染的——没解析完不画画面。
  3. 执行 JavaScript。普通 <script> 还会阻塞解析，这就是为什么脚本常放在 body 末尾。
  4. 布局（Layout）：算出每个元素的位置和大小。
  5. 绘制（Paint）：填充像素。
  6. 合成（Composite）：分层拼成最终画面。

这套流程里，"重排"（reflow）最贵——改动一个元素尺寸可能引发整棵树的重新布局。而只改颜色这类属性只需"重绘"，快得多。至于只影响合成的属性（transform、opacity），最快。

实用结论：页面卡，先别怪网速。打开开发者工具的 Performance 面板录一段，看看时间花在"网络等待"还是"渲染/脚本"上。这两个方向的优化手段完全不同。

七、这些阶段各自会怎么坏掉

把每一层的典型故障列一下，排错时能对号入座：

  • DNS 失败。症状是"找不到服务器"，浏览器提示 DNS_PROBE_FINISHED_NXDOMAIN。原因：域名过期、解析没生效、本地 DNS 有问题。
  • 连接失败。症状是"连接超时"或"拒绝连接"。原因：服务器宕了、端口没开、防火墙拦了、被墙。
  • TLS 失败。症状是红色警告页，提示证书无效/过期/域名不匹配。原因：证书到期、配置漏了某个子域名、系统时间不对。
  • HTTP 层失败。症状是 404、403、500 页面。原因：路径写错、没权限、后端崩了。
  • 渲染失败。页面能打开但样式全乱、或者白屏。原因：CSS/JS 路径 404、脚本报错中断执行、跨域被拦。

怎么快速分诊

ping example.com              # 能解析出 IP 吗？
ping 93.184.216.34            # 用 IP 能通吗？（Windows 默认禁 ping，可能误判）
curl -v https://example.com   # 一步步打印握手和响应头，最直观
nslookup example.com          # 单独验 DNS

curl -v 是这里最有用的一个：它会把 DNS 解析、TCP 连接、TLS 握手、请求头、响应头逐条打印出来，卡在哪一步一目了然。

八、性能优化的方向，其实就是减少往返

回头看整条链路，优化的本质就三条：

  • 减少往返次数。复用连接（Keep-Alive）、HTTP/2 多路复用、TLS 1.3 减一轮、QUIC 减到 0 轮。
  • 缩短往返距离。用 CDN，把内容放到离用户近的节点。
  • 减少往返数据量。压缩（gzip/brotli）、图片用 WebP/AVIF、按需加载、强缓存。

光速是绕不过去的。中美之间物理距离一万多公里，光在光纤里的速度大约是真空中的三分之二，单程理论极限就有约 60 毫秒。这就是为什么 CDN 不是"优化技巧"而是"物理必需"。

九、HTTP/1.1、HTTP/2、HTTP/3 差在哪

  • HTTP/1.1：一个连接同时只处理一个请求，浏览器只能开多个连接绕过去（通常 6 个）。队头阻塞明显。
  • HTTP/2：一个连接上多路复用，多个请求并发跑；头部压缩；服务器可以主动推送。基于 TCP，所以 TCP 层丢包还是会拖累所有流。
  • HTTP/3：改用 QUIC（UDP），把丢包影响限制在单个流内，连接迁移更好（换 WiFi 不断线）。目前主流大站基本都开了。
一句话总结：一次网页访问是解析→连接→加密→请求→响应→渲染六个阶段串起来的，每一阶段都可能单独失败。遇到问题不要靠猜，打开开发者工具的 Network 面板，或者 curl -v 跑一遍，看它卡在第几步，问题就定位了一半。
