ESP32 项目实践：从能跑到稳定跑的几道坎

2026-09-20 · 硬件 · 联网

ESP32 上手很快，把一个 LED 点亮挂到网上可能半小时就搞定。 但从「能跑」到「稳定跑几个月不出问题」，中间还差不少东西。 这篇写的是后者——那些只有在设备真的用起来之后才会暴露的问题。

一、Wi-Fi 断了要能自己回来

开发时连着好好的，实际部署后 Wi-Fi 掉线是常态： 路由器重启、信号被遮挡、邻居换了信道。设备必须能自动重连。

需要注意的实现细节：

  • 重连要退避。发现掉线就立刻疯狂重连，会让路由器把它当成攻击。 合理的做法是第一次等 1 秒，之后逐步拉长到 30 秒上限，连上后重置。
  • 重连不等于拿到 IP。前面提过，连上 AP 和拿到 IP 是两个事件。 重连逻辑要等的是拿到 IP 那一步。
  • Wi-Fi 掉线时正在做的事要能恢复。如果设备正在上传数据， 连接断开会返回错误，代码要能记住「这批没发出去」，下次连上补发。
  • 长时间连不上要有兜底。比如连续失败 N 次后重启设备， 这是最土但最有效的办法。很多商用设备就是靠定期重启撑住的。

二、别让网络阻塞主循环

ESP32 是双核的（C3 除外，它是单核），但网络操作仍然是耗时的。 一个典型的错误写法是在主循环里同步地等 HTTP 响应。

如果一次请求超时 5 秒，主循环就停 5 秒。对于要读传感器、 要刷屏、要响应按键的设备，这是致命的。表现是「界面卡住」「按键没反应」。

解决办法按复杂度排：

  • 拆成状态机。把「发起请求」和「处理响应」分成两步， 中间让主循环继续跑。这是最简单有效的改法。
  • 用独立的 FreeRTOS 任务。网络放一个任务，界面和传感器放另一个， 之间用队列通信。ESP32 的 SDK 本身就是基于 FreeRTOS 的， 用起来很自然。
  • 双核分工。经典版和 S3 是双核， 可以让一个核跑协议栈和网络，另一个核专注实时控制。 但要注意共享数据的保护。
关于「双核」的实际含义：ESP32 经典版的双核是 Xtensa LX6 双核， 240 MHz 下双核 CoreMark 跑分 1079.96，单核是 539.98。 数字上接近翻倍，但实际收益取决于你的任务能不能真正并行。 如果两个任务都在等同一个锁，多一个核也没有用。

三、内存要当回事

ESP32-C3 标称 400 KB SRAM，S3 是 512 KB，经典版是 520 KB。 看着不少，但这是芯片内总量，协议栈、Wi-Fi 缓冲区、蓝牙栈都要从这里分。

几个实际建议：

  • 看编译输出，别按标称值设计。编译完看 idf.py size 的结果， 那里有静态占用和剩余堆的真实情况。
  • 避免频繁的大块内存分配和释放。长时间运行的程序容易出现堆碎片， 表现为「刚启动好好的，跑几天就崩」。需要大缓冲的话， 启动时一次性分配好，之后复用。
  • 注意字符串拼接。String 类型的拼接在循环里会产生大量临时对象， 是嵌入式里很常见的隐性内存黑洞。需要格式化输出时， 用固定大小的 char 缓冲区加 snprintf。
  • JSON 要选对库。用那种把整个文档解析进内存的库， 一个稍微大的响应就能把堆吃光。选可以流式解析的， 或者干脆别用 JSON，用简单的文本协议。

四、OTA 升级要早做规划

OTA（空中升级）如果不从一开始就设计进去，后期加会很痛苦。 关键点在于分区表。

OTA 的机制是准备两个应用分区（通常叫 ota_0 和 ota_1）， 新固件写到空闲的那个分区里，写完校验通过后修改启动标志， 下次重启就从新分区启动。旧固件还留着，新固件起不来可以回滚。

由此推出的两条硬约束：

  • Flash 要够大。两个应用分区加上 NVS 等数据分区， 需要的 Flash 容量大约是单份固件的两倍以上。4 MB 的模组做 OTA 时， 应用分区能用的空间其实很紧张。
  • 要能回滚。新固件启动后要先做自检（比如连上 Wi-Fi、连上服务器）， 确认没问题再调用「标记为有效」。如果一直不标记， 看门狗重启几次后会自动回滚到旧固件。这个机制一定要用上， 否则一次失败的上传会让设备彻底失联，只能上门去接串口。

五、现场调试的几条退路

设备装到用户家里之后，你没法再插串口看日志。所以要提前留好后路：

  • 保留一个本地调试入口。可以让设备在按住某个按键开机时 开一个临时热点，连上去看状态页。这是最可靠的一招， 因为不依赖外网。
  • 把最近若干条日志存在 Flash 里。出问题时重启后还能读出来。 注意要限制条数和写入频率，Flash 有擦写寿命。
  • 加看门狗。硬件看门狗是防死机的最后一道。 主循环里定时喂狗，卡住就自动重启。
  • 上报设备自检信息。开机时上报固件版本、复位原因、可用内存， 这些数据在排查「为什么我的设备半夜重启」这类问题时非常有用。 复位原因可以从 SDK 拿到，能区分是掉电、看门狗还是软件主动重启。

六、一个实用的开发顺序

做完几个项目之后，比较省事的推进顺序是：

  1. 先把硬件点通。LED、串口、各个传感器单独验证，确认时钟和引脚没错。
  2. 再把网络跑通。能连上、能收发、断线能重连。
  3. 然后接上屏或者其它交互。这时候还没涉及业务逻辑，出问题好定位。
  4. 最后做业务逻辑，并且从这一步开始就考虑内存和长时间运行。
  5. 加 OTA、看门狗、日志留存这些「运维」功能。别留到最后， 因为分区表这类东西改起来要重新规划 Flash。

这个顺序的核心是每加一层都能单独验证。 反过来做——先把业务逻辑写完再回头查为什么连不上网—— 会同时面对好几个层面的问题，排查成本高得多。

关于稳定性：很多「不稳定的设备」其实不是芯片的问题， 而是没有处理好断线重连、内存增长、异常分支这几个点。 这些都不是难事，但需要从第一版代码就留着位置。 事后补的代价通常比一开始就写要大。
