API 设计：把接口写成别人愿意用的样子

2026-09-14 · API 系列 · 第二篇

接口能跑通，和接口设计得好，是两回事。前者只要代码不报错，后者要考虑的是：别人第一次看你文档，能不能猜对大半；出了问题，能不能一眼定位；半年后加需求，能不能不破坏已有的调用方。

这篇讲的是那些"踩过才知道"的经验。

一、先把"资源"想清楚

REST 风格的核心就一句话：用 URL 表示资源（名词），用方法表示动作（动词）。

好的：
GET    /articles          列出文章
GET    /articles/42       看第 42 篇
POST   /articles          新建一篇
PUT    /articles/42       整体替换第 42 篇
PATCH  /articles/42       局部修改第 42 篇
DELETE /articles/42       删掉第 42 篇

不好的：
GET  /getArticleList
POST /createArticle
POST /deleteArticleById?article_id=42
POST /article/update

为什么不好？因为把动作塞进了 URL。结果是每个程序员都会造出自己的一套命名，接口列表变成一锅粥，而且没法利用 HTTP 本身已经定义好的语义（比如 GET 应该是安全、可缓存的）。

复数还是单数

两种都有人用，但同一个项目里必须统一。常见做法是集合用复数（/articles），单个资源带 ID（/articles/42）。

层级别太深

可以：/articles/42/comments
别太深：/articles/42/comments/7/replies/3/likes

超过两三层就该考虑换个写法了，比如把深层资源提到顶层加查询参数：/replies/3/likes。

二、一致性比"好看"重要得多

接口设计里最值钱的不是某个技巧，而是一致。看三个例子：

  • 命名风格。要么全蛇形 user_name，要么全驼峰 userName，别混。混了之后调用方永远记不住。
  • 时间格式。统一用 ISO 8601（2026-09-14T12:34:56Z），别一会儿时间戳一会儿字符串一会儿 2026/09/14。
  • 分页参数。要么全是 page/page_size，要么全是 offset/limit，要么全是 cursor，别一个接口一个样。

一个反直觉的事实：一个稍微别扭但处处一致的接口，比一个单看很优雅但风格混乱的接口好用得多。

三、HTTP 方法该怎么选

每个方法有明确的语义约定，遵守它能让中间的各种设施（缓存、代理、日志）自动正常工作：

  • GET —— 只读，必须安全且幂等。绝不能用来改数据。也不要放敏感信息在 URL 里（会被记录到日志、浏览器历史）。
  • POST —— 创建，不安全也不幂等。重复调用会创建多个。
  • PUT —— 整体替换，幂等。调一次和调十次结果一样。适合"我提供完整内容，你给我存下来"。
  • PATCH —— 局部更新，理论上不必幂等，实践中很多实现是幂等的。
  • DELETE —— 删除，幂等。删一个已经不存在的东西，应该返回成功或者 404，而不是 500。

幂等为什么值钱

因为网络不可靠。用户点了一次提交，请求发出去但响应超时了——这时候客户端不知道到底成没成，要不要重试？

如果接口是幂等的，重试就安全；不幂等的话，重试可能造成重复下单、重复扣款。这就是为什么支付类接口会引入"幂等键"（idempotency key）这套机制。

四、错误响应：这里最容易设计烂

看看这个反面教材：

HTTP/1.1 200 OK
{"result": false, "err": -1001, "info": "系统繁忙，请稍后再试"}

问题一堆：用 200 表示失败、错误码是自己编的、错误信息笼统得没法用、调用方还得写两套判断逻辑。

好的做法：

HTTP/1.1 400 Bad Request
{
  "error": "invalid_parameter",
  "message": "字段 start_date 格式不正确，应为 YYYY-MM-DD",
  "field": "start_date",
  "request_id": "b3f1a2c4-8e7d-4a91-9c02-5d6e8f1a2b3c"
}

好在哪里：

  • 状态码表达类别，4xx 表示是调用方的问题。
  • machine-readable 的 error 字段（稳定不变），调用方可以按它分支处理，而不是去匹配那句会变的 message。
  • message 具体可执行，直接告诉用户改了哪个字段。
  • request_id 让你能在服务端日志里反查这一条。

状态码的具体含义见上一篇。

五、列表接口：分页、筛选、排序

列表接口的坑最多，因为它一定会遇到"数据量变大"这一天。

两种分页方式

  • 偏移分页（?page=3&page_size=20 或 ?offset=40&limit=20）：实现简单，可以跳到任意页。缺点有两个：数据量大时数据库要扫描前面所有行，越翻越慢；并且在数据频繁变动的场景下会漏项或重复。
  • 游标分页（?cursor=eyJpZCI6MTIzfQ&limit=20）：用"上一页最后一条的标记"作为起点。性能稳定，不会漏项重复。缺点是只能顺序翻，不能跳到第 50 页。

选择标准：后台管理系统这种要跳页的用偏移，信息流/聊天记录这种一直往下刷的用游标。

响应里要带上"还有没有下一页"

{
  "data": [ ... ],
  "has_more": true,
  "next_cursor": "eyJpZCI6MTIzfQ",
  "total": 1234
}

注意 total 这个字段是有代价的——算总数在大表上很贵。如果前端不需要显示总数，就不要返回它。

筛选和排序

?status=published&author=42&sort=-created_at&limit=20

几个经验：

  • 筛选字段用平铺的查询参数，别塞一个 JSON 字符串进去。
  • 排序用 sort=字段名，前面加 - 表示倒序，简洁好记。
  • 一定要给 limit 设上限（比如最多 100）。否则有人传 limit=999999，你的数据库就遭殃了。
  • 白名单控制可筛选、可排序的字段，绝不要把用户输入直接拼进 SQL。

六、版本管理：怎么改而不砸别人的饭碗

接口一旦发布就有人在用，而需求一定会变。核心原则：只做向后兼容的改动。

安全（兼容）的改动

  • 新增可选的请求参数。
  • 在响应里新增字段（调用方应该忽略不认识的字段）。
  • 新增接口。
  • 把必填改成可选。

破坏性的改动

  • 删除或重命名字段。
  • 把可选改成必填。
  • 改变字段类型或含义（比如原来秒现在毫秒）。
  • 修改 URL 结构。
  • 改变错误码的含义。

破坏性改动要做的话，得走版本化：URL 里带版本（/v2/articles）、请求头带版本（Accept: application/vnd.api+json; version=2）、或者域名区分。

代价要知道：URL 版本号（/v1、/v2）是行业里最常见的做法，也好理解，但它会带来一堆长期要维护的旧版本，代码里到处是分支。更经济的做法是尽量设计得稳一点，少升版本——把最容易变的字段放在一个嵌套对象里，将来改它就换那个对象，不动顶层结构。

七、几个具体的小决策

  • 字段缺失 vs null。要有明确约定。常见做法：字段一定出现，无值时为 null。这比"有时在有时不在"好处理得多。
  • 布尔值命名。用 is_active 这类带前缀的名字，别用 active（分不清是名词还是形容词）。
  • ID 类型。统一用字符串传 ID（哪怕内部是数字），避免 JavaScript 大整数精度问题。这个坑很隐蔽，用户量大了才会撞上。
  • 时间。永远存和传 UTC，带时区偏移或者 Z 后缀，由前端负责展示成本地时间。传"当前时间"这种概念最容易出时区 bug。
  • 金额。绝不用浮点数。用整数分，或者字符串。浮点数算钱迟早出问题。

八、认证和限流，别等出事再加

  • 认证用标准方案：长期凭证用 Authorization: Bearer <token>，会话用标准的 Cookie 属性（HttpOnly、Secure、SameSite）。别自己发明一套塞在自定义头里。
  • 限流要从第一天就设计。返回 429 时带上 Retry-After 和剩余配额的头（如 X-RateLimit-Remaining），让调用方能优雅退避。
  • CORS 是最小权限原则的典型场景：Access-Control-Allow-Origin: * 加上允许携带凭证，是个危险的组合，想清楚再写。

九、文档：接口的门面

再好的接口，文档烂就等于没有。几条实践经验：

  • 给能直接跑的例子。一个 curl 命令或者一段可复制的代码，胜过三段文字描述。
  • 写清楚错误情况。哪个参数错了会返回什么，比只写"成功返回"有用得多。
  • 标注幂等性和副作用。调用方需要知道"能不能重试"。
  • 给出真实的响应示例，包括那些可选字段。

如果有余力，用 OpenAPI（Swagger）这类规范来描述接口，能自动生成文档、生成客户端 SDK、做在线调试。前期一点的投入，后期省很多。

十、最后：从调用方的角度想一遍

设计完一个接口，拿它当陌生人去看一遍，问自己几个问题：

  • 不看文档，我能猜对 URL 和方法的组合吗？
  • 出错的时候，我能知道要改什么吗？
  • 这个请求失败了，我能安全地重试吗？
  • 半年后我加个字段，会不会把现在写好的客户端搞崩？
  • 我要抓 10000 条数据，会不会把服务器拖死或者被限流？

能答上这五条，接口基本就是"别人愿意用"的样子了。

小结。好的 API 设计没有高深技巧，就是三件事——用名词表示资源、保证处处一致、永远做向后兼容的改动。剩下的细节，都从这三点推出来。
