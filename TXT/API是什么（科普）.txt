一、什么是 API

API 是 Application Programming Interface 的缩写，中文一般译作"应用程序编程接口"。

这个定义听起来很抽象，其实用一个例子就清楚了。

你打开外卖 App 点了一份餐，App 上会显示"预计 30 分钟送达"。这个 30 分钟不是 App 自己算出来的——App 需要知道骑手现在在哪、前面还有几单、路况如何。这些信息都在外卖平台的服务器上。App 怎么拿到？通过 API。

放到更技术的层面说：

API 是一套约定好的规则，规定了两个程序之间怎么说话。

"我要查这个订单的配送进度"是一个请求（request），"预计 30 分钟"是一个响应（response）。请求长什么样、响应长什么样，都由 API 事先规定好。只要双方都遵守这个规定，就不需要知道对方内部是怎么实现的。

这就是 API 最重要的价值：解耦。

二、为什么需要解耦

假设没有 API。

每个想用地图功能的开发者，都得自己去理解地图公司的数据库结构、自己写查路线的算法。这既不现实，也不可能维护——地图公司一旦改了数据库，所有接入的开发者全部要跟着改。

有了 API 之后：

地图公司对外提供一个地址，比如 /route?from=X&to=Y，你只管往里传参数，它给你返回结果。数据库怎么改、算法怎么优化，那是地图公司自己的事，你完全不用管。

前台和后台从此可以各干各的。

三、几种常见的 API 形态

**REST API**

这是目前最常见的一种。核心思想是"用 URL 表示资源，用 HTTP 方法表示操作"。

比如一个博客系统：

GET /posts 获取文章列表
GET /posts/42 获取 42 号文章
POST /posts 新建文章
PUT /posts/42 更新 42 号文章
DELETE /posts/42 删除 42 号文章

GET 是读，POST 是建，PUT 是改，DELETE 是删。用起来很直观，因为 HTTP 本身就是这么设计的。

**GraphQL**

它想解决 REST 的一个痛点：请求太多了。

比如你要显示一篇文章和它的作者，REST 下可能要发两次请求（先拿文章，再拿作者）。GraphQL 允许你在一次请求里精确说明要哪些字段：

{
  post(id: 42) {
    title
    content
    author { name, avatar }
  }
}

返回的数据结构和你写的完全一致。好处是不多不少，坏处是服务端实现更复杂。

**WebSocket**

前两种都是"你问我答"。WebSocket 不同，它建立一条长连接，服务器可以主动推消息给你。

聊天室、实时价格、协同编辑都是它的典型场景。总不能让你每秒钟问一百次"有新消息吗"。

四、一次 API 调用的完整过程

以"查询天气"为例，把整个链路拆开看：

1. 你的程序构造一个 HTTP 请求，目标是 api.weather.com/v1/now?city=beijing
2. 请求头里带上认证信息（通常是一个 key），证明你有权调用
3. DNS 把这个域名解析成一个 IP 地址
4. TCP 三次握手，建立连接
5. 如果走 HTTPS，还要做 TLS 握手，协商加密方式
6. 请求发出去，服务器收到
7. 服务器验证 key、查数据库、组织数据
8. 返回一个响应，通常是 JSON 格式
9. 你的程序解析 JSON，拿到温度、湿度等字段

整个过程可能只有 200 毫秒，但上面每一步都可能出错。接口调试的复杂程度，很大程度上就来自这里。

五、关于 API key

大多数公开 API 都需要 key，它相当于一把钥匙。

需要注意几点：

**key 不能放进前端代码。** 前端代码是公开的——用户打开开发者工具就能看到。把 key 写在前端，等于把钥匙贴在门上。正确做法是在自己的服务器上做个中转，前端请求自己的服务器，服务器再带着 key 去请求真正的 API。

**key 要能撤销。** 万一泄露了，要能立刻作废，而不是只能等它自然过期。

**不同 key 用不同权限。** 一个 key 只能读，另一个能写。这样即使读的 key 泄露，损失也有限。

**注意配额。** 绝大多数 API 有调用次数限制，超了会返回 429 状态码。要做限流和缓存，不能每次都真的去请求。

六、状态码：API 的暗语

HTTP 状态码是 API 沟通时最精简的语言。

200 一切正常
201 创建成功了（对应 POST）
301 / 302 资源搬家了
400 你的请求有问题（参数错了）
401 你没登录 / key 不对
403 你登录了，但没权限
404 东西不存在
429 你请求太快了，先歇会儿
500 服务器自己出错了

**注意 4xx 和 5xx 的区别：4xx 是调用方的问题，5xx 是服务方的问题。** 排查时先看这个，能省一半时间。

七、给初学者的几点建议

**先读文档，再写代码。** API 文档会写清楚参数、返回值、限制、错误码。跳过文档直接试，往往要花更多时间。

**用工具先试通再写。** Postman、curl、或者浏览器的开发者工具，都能直接发请求。先在工具里把请求调通，确认参数和返回值，再写进代码。

**把错误处理写完整。** 只处理成功情况的代码是不能上线的。超时、限流、字段缺失都要考虑到。

**缓存。** 同样的数据不要重复请求。既省配额，也更快。

八、结语

API 是现代软件的地基。

你今天用的每一个 App，背后都在不停地进行 API 调用。地图、支付、登录、推送、统计——没有一个是自己从头实现的，全都是调用别人的 API。

理解 API，某种意义上就是理解现代软件是怎么被组装起来的。
